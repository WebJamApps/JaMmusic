## What this is

The React + TypeScript + Vite front-end for Web Jam LLC (the band site,
web-jam.com / webjamsalem). State via React **context providers**
(`src/providers/`) and **Redux** (`src/redux/`). The built front-end is
**embedded into the backends at build time** (web-jam-back → webjamsalem,
WebJamSocketCluster) and redeployed via a fan-out dispatch when `main` updates —
JaMmusic itself does not deploy to Heroku directly.

## Commands (get all green before declaring done)

- **Everything:** `npm test` — runs lint → **typecheck (`tsc --noEmit`)** → jscpd
  (copy-paste detection) → unit tests with coverage. This is the single check to
  confirm you're green — CI runs exactly this. ALWAYS run the FULL `npm test`
  before pushing; running the sub-scripts individually (`test:unit`, `test:lint`)
  skips typecheck/jscpd and lets a break reach CI.
- **Lint:** `npm run test:lint` (stylelint on `src/styles/**/*.scss` + eslint).
  Auto-fix with `npm run test:lint-fix`.
- **Unit tests:** `npm run test:unit` (vitest, run mode, with coverage, `TZ=UTC`).
- **Type-check only:** `npm run typecheck` (`tsc --noEmit`).
- **Dev server:** `npm run dev` (HTTPS Vite). **Build:** `npm run build`.
- e2e (`npm run test:e2e`, Playwright) needs a browser install (`npm run test:e2e:install`) and starts the app by itself. CircleCI runs it on every build, after the unit tests.

## Conventions

- **Snapshot updates:** use `npm run test:unit-u` (pins `TZ=UTC`) — never a bare
  `vitest -u`. Re-run `npm test` afterwards to confirm green (a bare update has
  bitten CI before).
- **Imports:** prefer the `src/` path alias over deep `../../../` relative chains.
- **Coverage gate (CI-BLOCKING):** `npm test` fails and the PR cannot merge if
  coverage drops below 90/90/80/80 (statements/lines/functions/branches). Any new
  component/function/branch you add MUST ship with tests in the SAME PR — check the
  coverage output at the end of `npm test` and get it green BEFORE opening the PR,
  not after CI flags it.
- **Tests** live in `test/`, mirroring `src/`; shared mocks in `__mocks__/`. Add
  or update specs alongside the file you change.

### PR body conventions (violations may be machine-rejected)

- **Summary**: markdown bullet points, one change per bullet — never a run-on paragraph.
- **Test evidence**: paste the REAL runner output verbatim (the lines showing pass/fail and test counts), inside a ``` fence — never a description like "all tests passed". If the output has scrolled out of view, re-run the test command and paste what it prints.
- **Test plan**: exact commands and concrete manual verification steps exercising the actual new behavior (start command, route/page, what to click, expected visible result) — a green test suite execution command (`npm test`) alone is not a plan.
- **Attribution**: `--author` names the model actually doing the work. Antigravity/agy sessions use the exact `displayName` of the model running, as listed in `ALLOWED_AGY_MODELS` in web-jam-tools `hooks/lib/check_agy_model.ts` (for example `agy — Gemini 3.8 Flash (High)`) — never any other model name (models misremember their own identity; copy the exact string).
- **Version bump ⇒ snapshot update & lockfile sync**: the AppTemplate footer renders the package.json version into a snapshot (`test/App/AppTemplate/__snapshots__/index.spec.tsx.snap`), and the version bump affects both `package.json` and `package-lock.json`. Running unit tests scoped only to modified files or affected suites (e.g. newly touched dialogs or utilities) omits `AppTemplate`, allowing snapshot mismatches (`AppTemplate > renders the component 1 mismatched`) to slip past local checks and fail CI. Whenever bumping the version (or rebasing a feature branch onto an updated `dev` base with a higher version), always synchronize `package-lock.json` (updating only the two root application `"version"` fields — root `"version"` and `packages[""].version` — or via `npm install --package-lock-only`; NEVER run a global search-and-replace across `package-lock.json`, which corrupts matching third-party dependency or peerDependency semver ranges like `^2.25.0`), update the `AppTemplate` snapshot with `npm run test:unit-u` (never bare `vitest -u` — the script sets `TZ=UTC`), update any version reference in the PR description, commit the updated snapshot in the same PR, and confirm with full `npm test` across all files before pushing.

## Troubleshooting & Guardrails

- **Vite Production Builds**: Local environment variables (e.g., `NODE_ENV=development` in `.env`) can bleed into `npm run build` and compile a development-mode bundle containing React development helpers. This causes a critical browser runtime crash with the error: `TypeError: (0, X.jsxDEV) is not a function`. To compile a pure, clean production bundle, always prefix the build command: `NODE_ENV=production npm run build`.
- **Playwright selectors for Material-UI Typography**: Material-UI's `<Typography>` component compiles to `<p>` tags (or other tags like `<h1>` or `<h6>` based on variants) by default, **never** `<span>` tags. Avoid utilizing tag-locked selectors like `span:has-text("...")` in E2E/Playwright tests, as they will timeout. Instead, use tag-agnostic text selectors like `:text("...")` or `p:has-text("...")`.
- **Running Playwright E2E Tests Locally**: `playwright.config.ts` defaults to `http://localhost:7878` and starts its own server (`npm run build && npm run preview -- --port 7878`), so `npm run test:e2e` tests your local code with no server started first. Run `npm run test:e2e:install` once to install the browser. Locally it reuses a server already listening on port 7878, so stop any old preview first. To run one spec, pass part of its file name: `npm run test:e2e -- <name>`. Set `BASE_URL` only to point the suite at a different server.
- **Draft PR Script Requirements**: The workspace `create-draft-pr.sh` script strictly requires the `--author`, `--summary`, `--test-plan`, and `--test-evidence` flags. Leaving any of these empty or as a default placeholder will cause the script to abort and refuse to open the draft PR.
- **Vitest Unit Tests and Environment Variables**: Local unit tests inspecting `checkIsAdmin` that parse `process.env.userRoles` must supply a fallback `userRoles` JSON string (e.g., `process.env.userRoles || JSON.stringify({ roles: ['admin'] })`) to be self-contained and pass on clean checkouts where `.env` is absent.
- **Distinguishing Socket Server Failures vs Empty Data**: In components consuming socket-fetched collections (`gigs`, `pics`), set state to `null` on connection failure/timeout (`CONNECTION_TIMEOUT_MS = 8000`) so components render inline error banners (`.gigs-error-message`, `.pics-error-message`) rather than rendering an identical empty UI state as a 0-item dataset (`[]`).
- **Worktree node_modules Symlink**: In temporary git worktrees, `node_modules` is not symlinked by default. Symlink the main repo's `node_modules` (`ln -s /home/joshua/WebJamApps/JaMmusic/node_modules node_modules`) so test tools (`tsc`, `stylelint`, `vitest`) are available. Unlink or exclude the symlink before committing.
- **TypeScript Number Comparison in Form States**: In `@mui/material` dialog forms, numeric fields (such as `gigInterval` inside form state) are
  typed as `number`. Comparing a numeric state variable against string empty (`form.gigInterval !== ''`) will cause a compilation error
  `TS2367: This comparison appears to be unintentional because the types 'number' and 'string' have no overlap.` Ensure you check
  `typeof form.field === 'number'` or keep form states properly type-separated.
- **Testing Library Jest-DOM Import**: In Vitest unit tests using DOM element matchers such as `toHaveAttribute`, `toBeInTheDocument`, or `toHaveTextContent`, always include `import '@testing-library/jest-dom';` at the top of the spec file to extend Vitest's `expect` matchers.
- **Date Formatting & Timezone Mismatch in Vitest Snapshots**: React date inputs and localized date string components render local time strings (e.g. `GMT-0500 Eastern Standard Time`) when snapshots are updated locally. On CircleCI Linux runners operating in `UTC` (`GMT+0000`), timezone mismatches break unit test assertions. Always run snapshot updates with `npm run test:unit-u` (or `TZ=UTC npx vitest run -u`) so snapshot outputs align with CI.
- **BackendUrl and Production Builds**: In production builds, `BackendUrl` defaults to an empty string indicating same-origin requests (`${BackendUrl}/song` resolves to `/song`). `vite.config.ts` carries a build-time guard that refuses production builds whenever `BackendUrl` resolves to `localhost` unless `ALLOW_LOCALHOST_BACKEND=true` is explicitly set (e.g., for local Playwright E2E suites). Running E2E tests with `ALLOW_LOCALHOST_BACKEND=true` compiles a local test bundle into `dist/` containing `localhost:7000`. Running `npm test` (specifically `test/build_backend_url.test.ts`) while that `dist/` directory exists will fail the assertion verifying that production dist assets contain 0 occurrences of `localhost:7000`; remove `dist/` (`rm -rf dist`) before running `npm test`.
- **E2E & Playwright CI Verification**: When an issue specifies continuous verification or execution in CI for Playwright/E2E tests, ensure `.circleci/config.yml` installs browser dependencies (`npx playwright install --with-deps chromium`) and executes `npm run test:e2e`, and ensure `playwright.config.ts` defines a `webServer` with `command: 'npm run build && npm run preview -- --port <port>'` (e.g. `npm run build && npm run preview -- --port 7878`) with a local default `baseURL` so production JSX runtime is generated without `jsxDEV` mismatch errors and E2E tests run self-contained in CI without manual external server startup. Furthermore, `playwright.config.ts`'s `webServer.env` must never rely on a bare fallback `process.env.userRoles || JSON.stringify({ roles: ['Developer', 'JaM-admin'] })`: ambient CI project settings can set an incomplete `userRoles` (e.g. containing only `Developer` or `admin`), which overrides the fallback and causes role-gated UI elements (`checkIsAllowed` filtering by `userRoles.indexOf(auth.user.userType)`) to vanish (`Error: element(s) not found` on `getByRole('button', { name: 'Admin' })`). `playwright.config.ts` must parse and union-merge required E2E roles (`Developer`, `JaM-admin`) into `webServer.env.userRoles`, and `.circleci/config.yml` must explicitly configure `userRoles: '{"roles":["Developer","JaM-admin"]}'` under the E2E test step's `environment` block. In addition, when rebasing a feature branch onto `dev`, ensure the semver version bump in `package.json` is preserved/updated relative to the new `dev` base.
- **Venue Form Optional Enums & Derived-With-Override Attributes (`familyNearby`)**: In `EditVenueDialog`, optional enum fields (`templateOverride`, `audienceAttention`, `venueType`) must never be sent as empty strings (`""`) in request payloads, as backend Mongoose schema validation rejects empty strings against allowed enum values; omit or delete empty enum values before sending. `familyNearby` is a two-mode field with server-managed `familyNearbyOverride`: when the client sends no explicit `familyNearby` key, the backend derives proximity from the venue address via `web-jam-back`'s `isFamilyNearby()` (geo-distance) with `familyNearbyOverride: false`; when a human explicitly toggles the checkbox, the client sends an explicit boolean (`true`/`false`), which the backend stores verbatim and sets `familyNearbyOverride: true` to protect the manual choice from address recomputes. The backend also supports `familyNearby: null` to clear the override and restore address derivation. The front-end therefore exposes a 3-state UI ('Auto-derived' vs 'Manual override') with an explicit 'Recompute from address' affordance when overridden, sending `familyNearby: null` on save to clear the override and restore derive-by-default, and omitting the key when untouched so existing override status or automatic address recomputes stay in force.
- **Queue Header Badges vs Widened Collections & Strict Mock Typing**: When widening an in-memory collection (e.g. merging sent pitches into outreach records for the Awaiting Reply panel), ensure dedicated queue badges (such as REPLY REVIEW QUEUE) maintain their own state tracking distinct queue items rather than reading the widened set. In unit test mocks, never use raw 'as any'; use strict casts ('as unknown as typeof ...') and explicit interfaces ('IpendingReply'). Additionally, ensure downstream filter side effects (such as venues with sent records being excluded from neverPitchedVenues) are explicitly protected by unit tests.
- **React Router Link vs Anchor in SideMenuItem & E2E Client Navigation Testing**: In `src/App/AppTemplate/SideMenuItem.tsx` (`ContinueMenuItem`), menu items with links containing `/music` only render as react-router `<Link>` components when the current route is on a music path (`isMusicPath && link.includes('/music')`). When on other paths (such as `/`), they render standard `<a>` tags. Therefore, E2E tests verifying client-side `<Link>` transitions must initiate from a music route (e.g. `/music`) to genuinely exercise React Router's `Link` component. In addition:
  1. Never wrap link clicks and assertions in `if (await link.isVisible())` guards, which silently pass if the link fails to render; use `await expect(link).toBeVisible()` so missing controls fail the test immediately.
  2. Prove no full page reload occurred by setting a window canary (`await page.evaluate(() => { window.__noReload = true; })`) before clicking and asserting `expect(noReload).toBe(true)` afterwards (full page loads reset window properties).
  3. When testing browser back/forward stack traversal, avoid building history with consecutive `page.goto()` calls (which trigger full browser page loads); construct history entries by clicking `<Link>` elements, then verify `page.goBack()` and `page.goForward()` navigate React Router's internal history stack.
  4. When testing `useSearchParams`, do not merely assert that the URL retains query parameters; assert that the component logic consuming the query parameter (such as `utils.initSongs` reading `?id=...` to enter single-song view) executes and renders the expected distinct UI state.
- **Strict Mock Typing and Avoiding Raw `as any` Across Unit and E2E Tests**: JaMmusic bans raw `any` / `as any` in both unit test mocks and E2E specs (`test/e2e/`). In unit tests, always apply strict casts using `as unknown as typeof <target>` or `vi.spyOn(target, 'method').mockResolvedValue(...)` so mock assignments satisfy TypeScript without dropping compile-time type safety. In Playwright E2E helper functions, type parameters explicitly with imported types from `@playwright/test` (such as `page: Page`, `route: Route`, `ws: WebSocketRoute`).
- **MUI Select `renderValue` vs `MenuItem` Test ID Collision**: When rendering customized chips or controls inside both a `<Select>`'s `renderValue` and its default/empty `<MenuItem>` (e.g. "no type" badge), never place the same `data-testid` on both elements. While the select menu is open, both instances are present in the DOM simultaneously, causing `getByTestId` queries to fail with an ambiguous element error. Maintain the canonical test ID exclusively on the `renderValue` child, and leave the `<MenuItem>` chip untagged or with a distinct option-specific test ID. Furthermore, ensure unit test mocks for `@mui/material`'s `<Select>` execute `props.renderValue(value)` so that test queries targeting elements inside `renderValue` resolve properly in unit test suites.
- **Sticky Table Headers & jsdom Styling Limitations vs Playwright E2E**: In jsdom unit tests with mocked `@mui/material` components (e.g. `TableCell` returning `<td {...props}>`), Material-UI `sx` properties (such as `position: sticky` and `backgroundColor: 'background.paper'`) pass through as raw object properties rather than being compiled by Emotion into computed CSS. Consequently, `expect(element).toHaveStyle(...)` will fail in jsdom for `sx`-driven styles. Unit tests should assert presence and semantic attributes, while visual and layout behaviors like sticky column pinning and opaque scroll backgrounds should be covered through browser E2E specs in `test/e2e/`.
- **Playwright Route Matching Across Path Separators (`**` vs `*`) and HTML Document Navigation Guards**: In Playwright's `page.route()`, single asterisks in URL globs (e.g. `'http://localhost:7000/venue*'`) do not match across path separators (`/`). Sub-routes and nested endpoints like `http://localhost:7000/venue/v1` will bypass the mock, fall back to the real network, and fail with `ERR_CONNECTION_REFUSED`. Use double asterisks (`'**/venue**'`) or a RegExp pattern (e.g. `/venue(\/|\?|$)/`) to intercept both collection and item/subresource endpoints. In addition, when matching API endpoints with broad patterns (e.g. `**/venue*`, `**/admin/user*`), guard against intercepting full-page HTML document navigations (such as `/admin/venues` matching `**/venue*`): always check `if (route.request().resourceType() === 'document') { await route.continue(); return; }` so Playwright serves the HTML bundle rather than returning mock JSON and crashing the page render.
- **Table Pagination, Default Sorting, and Inline Row Updates in E2E**: In tables with pagination and primary sort fields (such as sorting by `prospect` where eligible venues precede ineligible ones), inline editing of a sort field (e.g. toggling `outreachEligible` to `false`) moves the edited item behind other items upon refresh. If the dataset exceeds the page size (e.g. 10 items), the updated row can be pushed to page 2 and disappear from the DOM. Configure mock rows (such as setting other mock rows' `outreachEligible: false`) so the edited row remains stable on page 1 for post-update assertions.
- **Third-Party Script Races in E2E Suites**: External scripts loaded asynchronously (such as Google Maps API) can resolve mid-test and trigger conditional component replacement (e.g. replacing a `<TextField>` with an `<Autocomplete>`), wiping out form inputs typed before the script finished loading. In E2E suites where external services are not explicitly tested, abort external requests in `beforeEach` (e.g. `page.route(/maps\.googleapis\.com/, route => route.abort())`) to guarantee deterministic rendering and avoid race conditions.
- **Accessible Keyboard Navigation and Focus Indicators (`:focus-visible` without `outline: none`)**: When styling interactive controls, group buttons, or custom disclosure widgets (such as sidebar fold-open group toggles), never remove native keyboard focus with `outline: none;` without providing an explicit, contrasting `:focus-visible` outline (e.g. `outline: 2px solid var(--sidebar-fg-hover); outline-offset: 2px;`). Stripping outlines prevents keyboard-only users from seeing which control is active. Always verify keyboard navigation by focusing the control, confirming with `window.getComputedStyle` that `outlineStyle` is not `none` and `outlineWidth >= 1px`, and verifying that standard keyboard actuation keys (`Enter` and `Space`) expand and collapse the control.
- **WebSocket Mock Handshake in E2E Suites & Real Pointer Activation**: In E2E suites where WebSocket / SocketCluster connections are initialized, closing the socket abruptly (`ws.close()`) or leaving it unmocked triggers global network failure notifications (`commonUtils.notify(...)` via `Toastify`). The resulting fixed toast overlays (`.Toastify__toast-container--top-right`) intercept pointer events and cause locator clicks on header and sidebar toggles (such as `#mobilemenutoggle`) to time out. Always handle SocketCluster packets via `page.routeWebSocket` by intercepting `#handshake`, `#subscribe`, and `initial message`, responding with valid payloads (`{ id: 'fixture', pingTimeout: 20000 }`, empty collection arrays) to keep the app clean of error toasts. Furthermore, exercise real user interactions with `locator.click()` or `locator.tap()` instead of synthetic DOM events (`dispatchEvent('click')` or DOM `.click()`), ensuring Playwright verifies visibility, stability, and hit-testing without masking pointer-interception regressions.
- **Vitest Fake Timers for Date and Time Arithmetic in Unit Specs**: `test/vitest.setup.ts` activates fake timers for `Date` by default pinned to `1483228800000` (January 1, 2017 UTC, which falls on December 31, 2016 in US Eastern local time). Hardcoding future timestamps (e.g. `2026-10-10`) inside unit specs causes date diff arithmetic (`now - runDate`) to evaluate as negative time into the future, yielding negative millisecond spans or clock-skew fallbacks (`'just now'`). Hardcoded past timestamps in unit test fixtures must either be relative to `Date.now()` (e.g. `new Date(Date.now() - 48 * 3600 * 1000).toISOString()`) or set explicitly before December 30, 2016 (e.g. `2015-01-01`). Additionally, when testing components whose `useEffect` populates state asynchronously via `.then(...)` (such as `EditGigDialog` resolving `listVenues`), never rely on `await waitFor(() => expect(spy).toHaveBeenCalled())` followed by synchronous `screen.getByRole(...)`: the spy is invoked synchronously when `useEffect` starts, so `waitFor` can resolve before the `.then(...)` state update commits to the DOM (especially after shared fixtures call `vi.useRealTimers()`). Always use `await screen.findByRole(...)` (or assert the rendered DOM element inside `waitFor`) for elements rendered after async effect resolution.
- **AuthProvider Token Decoding in Playwright E2E Tests**: When seeding localStorage `auth` in Playwright E2E tests (`context.addInitScript`), `AuthProvider` inspects the stored token using `getTokenSub()`. If the token is not a valid base64-encoded JWT with an unexpired payload, decoding throws and resets auth state to unauthenticated (`defaultAuth`). E2E test fixtures must use a structured JWT containing a subject (e.g. `sub: 'user-123'`) and future expiration (`exp: 9999999999`), and must mock the corresponding profile retrieval endpoint (`/user/user-123`). In addition, when mocking `/user/user-*` for profile re-validation, always supply CORS headers (`access-control-allow-origin: *`, `access-control-allow-headers: *`, `access-control-allow-methods: *`) so cross-origin preflight `OPTIONS` requests from `customFetch` (triggered by the `Authorization: Bearer ...` header) do not throw CORS errors that trigger `AuthProvider`'s catch-block and unexpectedly reset the user to `defaultAuth`. Also mock background endpoints (e.g. `**/facebook/**`) to keep tests deterministic and prevent unmocked external scripts from triggering unintended UI fallbacks. Finally, wait for persistent structural milestones (such as `.menu-item` or `#mobilemenutoggle`) rather than content-dependent styling classes (like `.elevation3`, which only render when specific banner or card content is active).
- **Long-Running Operation Polling Lifecycle & Unmount Cleanup**: When triggering backend jobs (such as database backup or restore operations) that may take longer than standard request timeouts (e.g. Heroku's 30s limit), client-side polling must never be terminated by an arbitrary client-side attempt count (e.g. 30 attempts). Polling must continue until a server-authoritative terminal state (`completed` or `failed`) or fatal error is returned. Furthermore, own the polling lifecycle in a dedicated React effect or ref structure: cancel pending timer handles and flag cancellations upon component unmount, sign-out, or authorization/token changes so that in-flight network responses are safely discarded without updating unmounted or unauthorized sessions.
- **Backup & Operational Runs Table Size Column**: Per the MongoDB backup/restore design specification (`backup-restore/mongodb-backup-restore-design-2026-10-07.md`), backup run summary tables must include a dedicated `Size` column formatted with human-readable units (e.g. `B`, `KB`, `MB`, `GB` or an em-dash `—` for null/unrecorded sizes) alongside `When it ran`, `Trigger`, `State`, `Counts`, and `Dropbox path`, and collapsible detail/empty rows must account for the full column span (`colSpan={7}`).
- **Dialog Form State Reset on Open Transition Only**: In child dialog components receiving collection props that update during polling or parent refreshes (e.g. `runs: BackupRunSummary[]`), resetting form state in an effect that depends on the collection prop wipes out user-typed inputs (e.g. typed confirmation strings), in-flight operations, or completed operation results whenever the parent component re-fetches. Use a previous-open ref (`const prevOpenRef = React.useRef(false);`) and trigger form resets strictly on the closed-to-open transition (`open && !prevOpenRef.current`), leaving existing inputs and operation progress intact during background refreshes while the dialog is open.
- **Mocked MUI TextField in Unit Tests vs Browser DOM**: In `__mocks__/@mui/material.tsx`, `TextField` renders directly as an `<input>` element with applied props rather than an MUI wrapper `<div>` containing an inner input. Querying `screen.getByTestId('...').querySelector('input')` returns `null` in unit tests. When querying inputs in unit tests, handle both structures: `const el = screen.getByTestId('...'); const input = el.tagName === 'INPUT' ? el : el.querySelector('input')!;` so the lookup works seamlessly in both unit tests and real browser DOM trees.
- **Dynamic Imports and Vite Modulepreload Bundle Leaks**: When dynamically importing a heavy library (such as Mermaid via `await import('mermaid')`) inside a child component, importing that child component statically into a page entry file causes Vite's build-time modulepreload scanner to place chunk preload links into the parent entry chunk (`dist/assets/index-*.js`). This results in occurrences of the library's chunk name or symbols inside the entry bundle, violating bundle isolation rules. To ensure 0 occurrences of the library inside the entry bundle, mount the child component via `React.lazy(() => import('./ChildComponent'))` wrapped in `<React.Suspense>`.
- **Never Manufacture Safety or Verification Results from Fallbacks**: When consuming asynchronous or polling operations that perform critical data transformations or safety sanitizations (such as copying production data to DEV with PII scrubbing, email replacement, and read-back verification), NEVER synthesize or manufacture default "clean" or "successful" results (e.g. `clean: true`, `readBack: { status: 'none', message: 'clean' }`) when the server response lacks an actual operation result (`result: null` or omitted). An operation terminal state (`status: 'completed'`) alone does NOT prove that safety verification succeeded. UI components must require authoritative, validated result structures before displaying success banners or clean verification statements, and must surface an error or unverified alert if the result payload is missing, null, or malformed.
- **Fixture Type Checking over Raw `as any` in Unit Tests**: Avoid casting partial or ad-hoc objects `as any` in unit tests to test utility function fallbacks (such as date extractors or formatters). Reuse a fully typed fixture and override specific properties (e.g. `{ ...baseRunFixture, startTime: '...' }`) to preserve fixture type safety and adhere to the repository's strict no-raw-any rule. In E2E and component specs, define explicit payload interfaces (such as `IinquiryPayload`) or use `Record<string, unknown>` for intercepted request bodies and typed mock events (`as unknown as React.MouseEvent<HTMLButtonElement>`) rather than `any`.
- **Deep Structural Validation for Unknown API Results and Verification Consistency**: Type guard functions validating `unknown` API result payloads (such as `isValidRestoreResult` and `isValidCopyResult`) must deeply validate every record and nested collection consumed by the UI (e.g. ensuring row objects are non-null and contain required numeric/string fields, and index lists are valid arrays of objects) before returning true, rather than shallowly checking `Array.isArray(collections)`. Accepting shallow or incomplete records allows unvalidated items to crash UI render loops (e.g. calling `.toLocaleString()` on undefined/null counts). Furthermore, guards must validate the internal consistency of compound safety assertions: when an operation reports `clean: true`, it must require authoritative positive verification (`status === 'none'` and zero remaining violations), rejecting contradictory states (e.g. `clean: true` with a failed read-back or missing counts), and UI display components must never supply fallback defaults that convert empty or missing verification strings into "clean".
- **Conditional Predictions on Multi-Candidate Existing-Entity Warnings**: When building pre-save duplicate or existing-record warnings that match across multiple fields (e.g. name, city, address), never emit unconditional creation or outcome predictions (such as asserting that a different-city match "will result in creating a separate venue") when candidates in the target scope (such as same-city records) exist that could result in an update upon save (via street address normalization or address-less fallback). Warnings must remain conditional or omit the prediction, explaining the actual matching candidates, stating the backend save rules, and preserving the authoritative server-side outcome (e.g. HTTP 200 updated vs 201 created).
- **Status Indicator Alignment Across Multi-State Operation Results**: In result panels, operation summaries, or progress indicators reflecting asynchronous multi-state operations (such as batch dispatch or migrations that can be in progress, successfully completed, or stopped/partially failed due to server refusal/error), status icons and semantic theme colors (e.g., success, info, warning, error) must dynamically reflect the active state. Never leave a fixed success icon (e.g. `<CheckCircle />`) or success color (`success.main`) on panels displaying stopped, paused, or partially failed states, which misleads users into reading a refusal or partial stop as a success. Ensure stopped or refused states use warning/error indicators (`<Warning />`, `warning.main`), active states use progress indicators (`<CircularProgress />`), and completed states use success indicators.
- **Inquiry Form Metadata, Spam Protection & Booking Fields**:
  - **Single Source of Truth in `formData`**: When collecting form metadata (such as `form`, `website`, `formLoadedAt`), initialize all fields once in component state (`formData`) and require callers to explicitly supply the form identifier (`<Inquiry form="webjam-homepage" />` or `<Inquiry form="jam-bookus" />`). Avoid redundant prop-threading through intermediate form components, and do not re-merge or overwrite state in submission click handlers.
  - **No Submission-Time Load-Time Fallbacks**: Never supply submission-time fallback defaults for interaction timestamps (e.g. defaulting `formLoadedAt` to `Date.now()`). Defaulting to the current time at submit time yields `now - formLoadedAt ~ 0ms`, falsely tripping the backend's minimum human interaction speed check (< 3 seconds) and rejecting valid submissions as bot spam.
  - **Booking Fields Validation & Google Places Autocomplete**: Client-side validation requires `eventDate`, `eventType`, and either `venuePlaceId` or `venueAddress` for Book Us (`jam-bookus` / `showBookingFields`), while the Homepage inquiry form remains unconstrained. If `GOOGLE_MAPS_API_KEY` is missing or Google Maps script fails to load, `VenueAddressInput` gracefully degrades to a manual text input with an informative note and submits `venueAddress`. When a suggestion is picked, `venuePlaceId` is submitted and `venueAddress` is omitted.
  - **Testing Autocomplete with Listbox Roles**: In Vitest / testing-library tests, native `<select>` options also have `role="option"`. When asserting suggestion items in custom dropdowns, scope queries to the suggestions listbox (`within(screen.getByRole('listbox')).getAllByRole('option')`) to avoid collisions with country/state `<select>` options.
  - **Preserve Intervening Form State & Bound Async Third-Party Lookups**: When an autocomplete or suggestions component performs async secondary requests (such as fetching place details via Google Places), never spread stale form state captured at click time when the promise resolves. Read the latest form state from a ref (or updater function) so intervening customer edits to other fields are preserved, and discard the async completion if the user has since changed the input or selection. Furthermore, every third-party loader and lookup request (script loading, library imports, predictions, and details) must be guarded with bounded timeouts, so that if the external service hangs or fails to answer (neither resolving nor rejecting), the component gracefully degrades to manual input with the latest typed text rather than leaving submission disabled indefinitely. Late responses arriving after fallback must be ignored.
  - **Relative Future Dates in E2E Browser Form Validation**: In Playwright E2E tests validating date pickers with "today or later" constraints, never hardcode static calendar dates without freezing the browser clock. Use relative future dates computed from `Date.now()` (e.g. `new Date(Date.now() + 30 * 86400000).toISOString().slice(0, 10)`) and assert the dynamically computed date in intercepted submission payloads so tests do not expire and fail after static calendar dates pass.
  - **Clean E2E Test Listeners**: Never leave temporary debug listeners (`page.on('console', ...)`, `page.on('pageerror', ...)`) active in checked-in Playwright E2E test suites.
- **ESLint `unicorn/prefer-classlist-toggle` in Theme and Class Synchronization Effects**: When updating DOM class lists based on reactive boolean state (such as syncing theme `dark-mode` onto `document.documentElement`), ESLint's `unicorn/prefer-classlist-toggle` forbids manual `if (active) el.classList.add(...) else el.classList.remove(...)` branches. Always use `el.classList.toggle('class-name', booleanCondition)` directly.
- **Review Lifetime Invalidation for Async Modal & Preview Updates**: When an asynchronous operation (such as re-generating or updating an email preview via `getPreview`) is triggered inside a modal dialog (such as `OutreachDialog`) or review flow:
  1. **Capture Review Generation**: Both the parent coordinator (`AdminOutreach`) and the modal dialog must capture the active review generation (`reviewVersion.current`) before initiating the request.
  2. **Invalidate Across Dialog Close & Session Changes**: If the user closes the dialog or switches review sessions (which increments `reviewVersion` and clears drafts), any subsequent resolution or rejection of in-flight promises must be ignored.
  3. **No Phantom State Updates**: Stale resolutions must never update parent preview collections (`setPreviews`), dialog customization state (`setRebuilt`), error state (`setUpdateErrors`), or loading spinners (`setUpdatingVenueId`). Allowing stale responses to commit after close/reopen causes phantom `Edited` marks, corrupts new review previews with old dates, and creates fingerprint mismatches that fail batch dispatch.
  4. **Deferred Request Regression Coverage**: Test suites must include regression tests that initiate an update, close and reopen the review session while the request is in flight, resolve the deferred promise, and verify that stale drafts, previews, and customizations are cleanly discarded.



## Branch & memory hygiene

- One branch per task: never create or push any branch other than the one
  created for the current task.
- Once your PR is merged or closed, its branch is DEAD — never commit to it or
  push it again. Follow-up work (including afterthoughts like docs or lessons
  learned) starts on a NEW branch off the latest `dev`, with its own PR.
- Save lessons BEFORE the merge, not after: anything you learned during the task
  worth keeping (build quirks, selector gotchas, testing patterns — e.g. the
  output of a `/learn`-style memory pass) gets committed to this file's
  Troubleshooting/Memory sections on the SAME task branch while the PR is still
  open, so it ships inside the PR. A post-merge push to the old branch strands
  the lesson and forces manual cleanup.
- Extend existing guidance over adding duplicate rules: when folding lessons learned
  into instruction files like `AGENTS.md`, never create a new standalone entry
  that duplicates pre-existing rules (such as full-suite verification, snapshot updates,
  or version bumps). Locate and extend the existing canonical rule with the new specifics,
  maintaining a single source of truth without duplication.

## Snyk and security audits

- If a task involves resolving Snyk security failures in a PR or build, and you cannot access the Snyk reports locally (e.g., due to local authorization or API limits), always ask the user to provide the exact Snyk failures and vulnerability IDs first. Do not attempt to guess or audit blindly, as this can lead to going down the wrong path.
- For tasks specifically targeting the resolution of PR checkers, GitLab/GitHub actions, or Snyk security checks, you should proceed with committing and pushing the changes (once local tests and linters are verified green) so the remote pipelines can actually execute and validate the fixes, rather than leaving them as uncommitted working tree edits.
- **No Insecure Version Downgrades or False Suppressions in `.snyk`**: Never downgrade a dependency to a lower version (e.g., pinning `deepmerge` to `4.1.2` to bypass `>=4.2.0` advisory ranges) and never add an ignore entry in `.snyk` asserting that the downgraded version is secure. Downgrading removes upstream prototype-pollution protections and exposes consumers to property injection. Instead, replace vulnerable packages with secure drop-in replacements via npm package aliases in `package.json` `overrides` (e.g., `"deepmerge": "npm:@stackline/deepmerge@^1.1.0"` for CVE-2026-93753) and add regression test coverage asserting that dangerous keys (like `__proto__`) are rejected or sanitized without prototype pollution.
